# Combined delivery, core thread: notes per stage (for the lead; not a permanent doc)

## S3 (build 3.4.1.52 once the lead squashes; upgrade step 10 "SavedVariables performance cleanup")

### What changed
- **Upgrade step 10** (`PSS_Upgrade.lua`, five parts, all safe to run twice, none "always"): the Camelot name repair, the 1500 cap, found members stamped then every record saved sparse, the players' switches, the custom filter ids. `showIgnoreDebug` is in `RETIRED` and no longer written (`ResetIgnoreDB`, step 1 backfill gone). Report keys: `guilds.camelot`, `guilds.capped`, `players.camelot`, `players.flags`, `filters.customIds`, `cleanup.sparse`.
- **Sparse guild members** (core `PSS_GuildIgnoreList.lua`, the `-- (member fields)` block, `check_fields.lua` still guards it): `_playerKey` (when equal to the key), `_canon`, `_gkey`, `_managed`, `_virtual`, `name` (when `displayPlayer(key)` gives it), `guild` (when it is the rule's name) and the "Managed list" date are not saved. Accessors find a record's key from one weak map `homeKey` (record to stored key, filled in one walk the first time a record is missing, emptied by `markMemberIndexDirty`; **not** filled by the member index, so a chat-only session never pays for it) and its rule by looking the key up in the rules. `memberShipped(m, g)`: a record with no date in a managed rule is a shipped member (found members always have a date; step 10 stamps one on any found member that lacks it). Records are made sparse by `compactMember(m, k, g)` inside `compactAllMembers()` (step 10, logout), and a changed shipped member is saved sparse by `PSS_FlushManaged`. A shipped mark or date in a rule that is not managed is kept (the real 3.4.1.50 save has one such record: `skzm`).
- **Counts**: `History.CompactCounts` (zero types and a total equal to the sum are not saved) for members, players, custom filters and built-in stats (at logout through `PSS_CollapseFilters`, `M.PSS_CompactPlayers`). Readers already use `EnsureCounts` / `CountTotal`.
- **memberCount**: not written (`storeMemberCount` returns the count, `bump`/`tidy` gone), dropped from every rule at step 10 and logout; schema `guildOld`.
- **Cap 1500** (`M.PSS_CapMembers`, `M.PSS_CapAllMembers`, step 10 and the logout flush): the oldest members holding nothing of their own (no note, W I G P C choice, counts, history) go; a rule can stay over the cap when every member has something.
- **Player W I G P C**: a switch is saved only when false; a missing one blocks (`p[f] ~= false` everywhere: `anyBlocked`, `AddToList`, `ensurePlayer`, `PSS_SetPlayerSetting`, the block source's `decide`; `PSS_PlayerAllowed` and the Players query already read `== false` / `~= false`). `M.PSS_CompactPlayers(legacy)` (step 10 with `legacy`: a record from before guild invites got its own switch takes the party invite one; logout without). Exports fill every switch (`p[f] ~= false`); import stores a blocking switch as nil.
- **Log group `m`** (`PourSocialScore_Logging/PSS_SavedLog.lua`): not saved when it is `M.PSS_DisplayPlayer(owner key)` for a `p:` / `g:` group; `false` when a person's lines have no name (nil would read as derived); unpack derives it.
- **Custom filter ids** (`PSS_ChatFilters.lua`): `M.PSS_NewFilterId()` (`nextFilterId`, routed to `PSS_RulesDB`, only goes up, stays above any number id found), new and copied filters get one, step 10 gives the existing ones one (`M.PSS_AssignCustomFilterIds`, loads Logging first when a filter may have lines) and `History.RenameOwner` moves the outbox lines, recent counts (session, day, slots), log lines and keep from `f:t:<text>` to `f:<id>`; two filters with the same text: the first takes the history. Editing a filter keeps its id (history); a copy gets its own. The tidy (`PourSocialScore.lua`) now judges `f:<number>` owners and keeps lines still under a filter's text. A filter saved with no id by an older version keeps working under its text key until the next step 10.
- **Camelot name repair** (`PourSocialScore_Libraries/PSS_Camelot.lua`, new file in the three Libraries TOCs; the core loads Libraries only on a Camelot save, interface under 20000 and realm `ClassicBetaPvP*`, that holds a name): a stored member keyed `first-last` with a faction and no `_playerKey` (`M.PSS_MemberHasPlayerKey`) goes into the shipped member (`M.PSS_MergeIntoShipped`), else into its stored twin (`M.PSS_MergeMember`), else is stored again as `first last-<realm>`; Player Ignore List entries (and their records, the entry already listed under the repaired name wins) and `delList` names the same; block lines and recent counts follow (`History.RenameOwner`). `mergeMemberRecord` no longer copies `name`, `guild`, `whenBlocked` or `_` fields.
- **Schema map**: `memberCount` to `guildOld`, the runtime member fields to `memberOld`, notes on the sparse forms; `nextFilterId` in `LAYOUT.rules`.

### Deviations, decisions and open questions for the author
1. **A custom filter with a number id is dropped by 3.4.0.29** (and any build before 3.4.1.47): the harness shows its Chat Filters loop treats an id it does not know as "a built-in that no longer exists". Downgrading to 3.4.0.29 after step 10 loses the custom filters (3.4.1.47 and later keep them). Plan decision 3 asked for number ids; the alternative is to keep `filterID` `""` and put the id in a table keyed by position, which U3 ruled out. Recommend: accept (3.4.0.29 is the live release but a downgrade past U3 was already unsupported, 2.3 item 8).
2. 3.4.0.29 and 3.4.1.50 and older read a migrated save without error and with the same member counters, but: they show an empty Player Ignore List (S2b, not S3); a record without a date counts as an extra member while the shipped lists are not loaded (+254 in `membersShown` on the author's save); a player whose party invite is allowed and guild invite blocked (switch missing in the file) reads as both allowed (older `ensurePlayer` copies the party switch).
3. One member on the author's 3.4.0.28 save carried the shipped mark and a real date: it now reads "Managed list" like every shipped member (the dump normalises it).
4. The "first name only" listing (a name that lost its surname) cannot be detected for sure: step 10 names Player Ignore List entries spelled `Name-Classicbetapvp` that have a faction (found by a unit) as "may have lost their surname". The author's saves have an empty list, so it printed nothing on them.
5. The cap is enforced at the upgrade and at every logout flush, not on each capture (a sweep can pass 1500 in a session and is cut at logout).
6. The unique-text rule for two filters sharing text: the first filter takes the shared history (counts are per filter and unchanged).
7. Log group `m = false` is written for a `p:` / `g:` group whose lines have no member name (only in tests so far).
8. Step 10 loads Libraries only on a Camelot save with saved names, and Logging only when a custom filter without an id may have lines.
