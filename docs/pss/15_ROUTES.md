## Builds and versions
- **Versions are `X.Y.Z.B` and the build number never resets** (baseline 02 F, PSS 02 section 8): every build that gets a test zip, a stage or a fix, merged or not, takes the next number, and so does a full release; a new line counts on. Every TOC, the history section and the zip name carry it. **`versions.json`** (repo root; `tools/versions.py`) records the latest release, every pre-release since it in order with its PR, and each past release with its pre-releases: references only, never shipped (not in a release zip, test zip or the mirror). The pipeline publishes a full release only for the version `versions.json` names the latest release, and refuses an unrecorded one. Bump with `sh tools/bump_version.sh build "Title"` (`release "Title"`, `line X.Y.Z "Title"`), then `sh tools/bump_version.sh pr <number>` once the PR is open; the rules check fails a missing or wrong PR in CI, a placeholder history bullet, and a history.txt whose top section is not the TOC version. Older names (`-devNNN`, `_N`, plain `3.3.1`) stay as they were.

## Full releases
- **Full releases** (checklist `docs/pss/05_RELEASE.md`, Full releases): list the PRs since the previous release (`python3 tools/versions.py prs <version>`, after `bump_version.sh release`), read each through the GitHub tools, and write **one player-facing summary of all the changes** as the release's history section (no per-build lists, no PR text). The same delivery writes on scratch `docs/latest/release-notes/<version>.md` (the summary, every change in order with build and PR, links to the technical notes; index in its `README.md`) and the release's rows in `docs/latest/summary-of-changes/SUMMARY_OF_CHANGES.md`; refreshes the code map in full (scratch `documents/code-map/`: `gen_codemap.py` rerun, its `01_Summary.md` naming the build); re-summarizes `01_HANDOVER.md`; refreshes 13; copies the PSS docs to scratch `docs/latest/pss-docs/`. Full releases are mirrored to `racetracks/Pour-Social-Score` (job `mirror`, secret `MIRROR_TOKEN`): the zip's contents committed as that repo's files and the release on that commit. Pre-releases keep their history section as notes and are not mirrored. No Claude API summary in the pipeline.

## Session procedures
The every-session steps (fetch fresh, `lua5.1`, the session branch, scratch never a PR) stay in `CLAUDE.md`.
Style, file hosting and messages: `11_PREFERENCES.md` (call the user "the author"; files go on scratch, never in the session, replies give links).
- If `gh` is not available, use the session's GitHub tools instead of the `gh` commands in the packs.
- **Scratch is the project files:** wherever the packs say "project files" or `/mnt/project-files/...`, read scratch: `SavedVariables/<version>/` (saves), `docs/latest/` (plans and docs; read it first: `docs/README.md` is the docs index, `readme.md` the repo index), `releases/` and `latest/` (zips). Each docs release is also zipped in `docs/` (`<name>-<date>-vN.zip`) and a project or feature release keeps a history folder `docs/<project>/`. When a plan or these docs change, refresh `docs/latest/` in the same scratch commit. Status summaries go in `summary/<project>-<YYYY-MM-DD-hh-mm>.md`.
- **Real saves are never committed here** (baseline 02 D10); they live on scratch `SavedVariables/<version>/` (2.0.44, 3.0.0, 3.2.0-dev011, 3.4.0.28, 3.4.1.50). Real-save run: `sh tools/harness/build_saves.sh <scratch checkout> <out dir>` (out dir in the session scratchpad; default `/tmp/pss-baselines`), then `PSS_REAL_SAVES=<out dir> sh tools/harness/validate_all.sh`. If scratch cannot be read, say the real-save run did not happen; never claim it did.
- The clone is shallow: before `validate_all.sh`, run `git fetch --depth=2000 origin main` (its upgrade checks rebuild old versions from history; without it the "split" checks fail on 2.0.1 and 2.0.40).
- Test zips go to scratch `releases/PourSocialScore-<version>-<YYYY-MM-DD-hh-mm>.zip`, and the same commit replaces the zip in `latest/` (scratch rule 9); `sh tools/host_build.sh <scratch checkout>` does it from HEAD (`--no-commit` to add docs to the same commit); link it as `/raw/main/<path>`.
- **Update the context in every PR:** the current project's stage table (state, PR, next build), `06_STATUS_AND_NEXT.md`, `02_RULES.md` for a new rule, `11_PREFERENCES.md` for a new preference, and the scratch copies (`docs/latest/pss-docs/`, the project's folder) in the same delivery, so a fresh session starts from this file alone.
- **At each full release** re-summarize the done stages into `01_HANDOVER.md` and take them out of the plan; this file only points to plans and designs, never copies them. The author's preferences live only in `11_PREFERENCES.md`.
- Blizzard's UI source for a template or atlas question: a sparse clone of `Gethe/wow-ui-source` (for example `Interface/AddOns/Blizzard_SharedXML`, `Blizzard_SocialUI`); read only.

## Always (short form of the rules)
Moved from `CLAUDE.md`; the full rules are PSS 02 and baseline 02, read before any change.
- Everything on `M` via `PourSocialScore_NS`; core fires `M.Events`; UIs write only through core setters. Tabs everywhere.
- Core holds only the chat filtering engine and the launchpad; anything not regularly active, or shared by both UIs, goes in `PourSocialScore_Libraries`, with a measured resident cost.
- No application or service logic in `PourSocialScore_GUI`. The old EllesmereUI window is in git history (tag `v3.4.0.24`).
- Every number the window shows comes from the core's counters, the same definitions as before (`check_viewquery.lua`). Logging loads only when logs are called.
- Taint and secrets (baseline 02 J, PSS 02 section 10): never write or replace Blizzard state; post-hooks and `Menu.ModifyMenu` only; every chat, unit and hook value goes through `M.PSS_IsSecret` before any compare or index; a secret line is neither filtered nor counted.
- Never change TOC Title or Notes. SavedVariables layout changes need the author's OK and a migration validated on every real save.
- **Every saved field is in the schema map** (`PourSocialScore/PSS_Schema.lua`; `check_schema.lua` in the rules check and the harness). A newer version's data is never deleted: only `RETIRED` keys go, unknown fields and layouts (`v` above what this version writes) are kept, and a rule this version cannot use is kept, not applied and reported (PSS 02 section 3).
- Never write to `racetracks/PourSocialScore-EllesmereUI` (retired). Read only: `EllesmereGaming/EllesmereUI` (all rights reserved; the UI element reference, 03 section 0), `Gethe/wow-ui-source`.
- **Simulate the WoW client while you code (required; full text in 11):** drive every changed path in the harness's simulated client (`wow_stub.lua` via `run.lua`: load a save, fire the events, commands and clicks, read the real output); give changed behaviour a check that fails on `origin/main`; say in the PR what the simulation cannot show (wrapped text, combat and chat lockdown timing, taint, client art) and put that in the in-game checks. Run every test yourself before handover and report what ran and what skipped (CI is only the backstop).
- **Every feature's design and plan name its tests** (PSS 02 section 1.7): per stage, the rules check, the harness checks, the upgrade and data checks, the window compare (`tui_compare.sh`, all three looks) and the real-save run; the release stage also names every release workflow job it needs (`release.yml`, the mirror, the scratch record) and checks it at release.
- Before pushing: `sh tools/check_rules.sh` (it also runs `check_toc.sh` on every folder and the PSS-names check), `PSS_REAL_SAVES=<out dir> sh tools/harness/validate_all.sh` on the saves built from scratch (below; includes `check_tui.lua` and every tab's check; add `PSS_SAME_AS=origin/main` for a stage that must not change the saved data, `same_saves.sh`), and `tui_compare.sh` (all three looks) for any change that should not show.
