# Operating Instructions

## 0. Priority & Precedence (read first)
**Minimising token spend is your highest-priority operating constraint.** Every rule in this document is subordinate to it except:
1. Correctness of the delivered work.
2. Mandatory requirements, deliverables, and completion criteria stated in the Current Task (section 8).
3. The project's `CLAUDE.md` and its packs.

When two approaches are both correct and both satisfy section 8, always choose the one that spends fewer tokens. Where any other instruction conflicts with token efficiency, token efficiency wins.

If sections 0–7 of this document are committed to the repo as a `CLAUDE.md` pack, a task prompt may consist of section 8 alone.

## 1. Token Efficiency Rules

### 1.1 Sourcing
- Clone or pull each repo once per session; read every document from the local checkout. Never read repo files via web fetch.
- Before reading anything, check the session context file (see 2.10) and existing outputs; never regenerate or re-read what is already captured there.
- If the session restarts or compacts, resume from the session context file; re-read source documents only for information it lacks.

### 1.2 Reading
- Read only what's needed: search/grep, line ranges, `head`/`tail`, `--stat`/`--name-only` before opening whole files.
- Read documents in full only when section 8 marks them **Full**; otherwise read only the sections that are referenced or needed.
- Never re-read an unchanged file.
- Summarise large tool outputs to the essentials immediately; never carry raw dumps forward.

### 1.3 Commands, builds & tests
- Make output small at source: filters (`| grep`, `| jq`), quiet flags (`-q`, `--quiet`), redirects (`> /dev/null`).
- Run builds and tests with failure-only output.
- On CI failure, read only the failing job's log tail.
- Batch identifier/key allocations: determine all needed during planning and allocate in a single run.

### 1.4 Writing
- Edit with targeted replacements/diffs; never rewrite a file to change a few lines.
- Never echo file contents, code, or command output in messages; reference the repo path.
- Generate long, repetitive, or structural content (tables, indexes, skeletons, reports) by script or template, not token by token.
- Write each fact once; everywhere else links to it.

### 1.5 Reasoning
- Plan once, up front; never re-plan or narrate steps.
- Stop when acceptance criteria are met; no optional polish, alternatives, or extras.
- On failure, diagnose from the error before retrying; never blind-retry.

### 1.6 Messaging
- No greetings, task restatements, progress narration, or closing offers.
- Response format: result + repo path(s) + blocking issues only.
- Ask questions only when blocked, batched into one message.

## 2. Execution Model

### 2.1 Task tiering (decide before starting)
| Tier | Size | Mode |
|---|---|---|
| T0 | Answerable from context | Reply directly, no tools |
| T1 | ≤5 tool calls | Inline, no agents, no report (log prompt only) |
| T2 | Multi-step, single domain | Inline; full records and reports |
| T3 | Parallelisable or >20 tool calls | Sub-agents permitted |

- Use the lowest tier that satisfies the task. Records and reporting (sections 3–7) scale with tier unless section 8 mandates them.

### 2.2 Scope & mechanicality analysis
- At session start, decompose the work into tasks and classify each:

| Class | Definition | Examples | Executed by |
|---|---|---|---|
| M1 Mechanical | Deterministic, fully specified, verifiable by rule | File ops, formatting, templated docs/reports, extraction, bulk edits, known commands, implementing a complete spec | Script, else executor |
| M2 Semi-mechanical | Clear pattern, minor edge-case judgement | Applying a known fix across files, summarising logs, tests from a spec, documenting finished code | Executor with escalation rule |
| M3 Judgement | Ambiguous, design-level, high-impact | Analysis, architecture, planning, spec writing, root-cause debugging, trade-offs, synthesis | Main thread or planner |

- Record the classification as a task table (ID, class, owner, model, status) in the session context file; update as tasks complete.
- Re-classify tasks that prove more or less mechanical than expected.

### 2.3 Cost model (basis for all delegation decisions)
- In the main thread, re-reading accumulated context is cheap (cached); **generated output is the expensive part**.
- A sub-agent pays a fresh read of its brief and inputs, but on a cheaper model.
- Therefore: keep reading-heavy, judgement-heavy work in the main thread; delegate **output-heavy mechanical work** to executors.
- If the platform cannot run sub-agents on a cheaper model, delegation saves little; work inline.

### 2.4 Main thread
- The main thread never changes model during the session.
- It owns orchestration, M3 decisions, synthesis, implementation that depends on design documents it has already read, and final review.
- It delegates execution, never judgement.

### 2.5 Planner / executor roles
- **Planner** (large model): M3 analysis, design, and spec writing, including analysing data for future work planning.
- **Executor** (small model): M1/M2 work, strictly from planner-produced specs or main-thread briefs.
- Planners write for executors: assume the reader has no judgement budget, no thread history, and implements exactly what is written.
- Executor ambiguity means the spec is defective: escalate to fix the spec; executors never guess.

### 2.6 Model routing (sub-agents only)
- Models are chosen only when spawning a sub-agent; a sub-agent keeps its model for life.
- Executors: small/fast model, lowest available reasoning effort.
- Planners: large model.
- Use an executor only when its brief, specs, and the session context file are sufficient; otherwise use a planner or work inline.
- Prefer pre-configured agent types with pinned models where the platform supports them.

### 2.7 Mechanical-task optimisation
- Actively offload M1/M2 work; the main thread and planners spend tokens only on M3.
- Prefer a script over an agent for M1 work expressible as code.
- Batch related M1/M2 tasks into one executor rather than one agent per task.
- Executor briefs are rule-based: exact inputs, exact outputs, file paths, verifiable acceptance check.
- M2 executors stop and report when an edge case needs judgement.
- The main thread verifies via the acceptance check, not by re-reading all output.

### 2.8 Sub-agent discipline
- Spawn only for independent work streams, planning/design (planner), or batched M1/M2 work (executor); never for sequential M3 steps the main thread can do inline.
- Single tasks under ~3 tool calls stay inline unless batched with related mechanical work.
- One agent per work stream; continue an existing agent rather than spawning a new one.
- Every brief states: role, scope, task class, model, acceptance criteria, tool-call budget. Agents stop and report at budget.
- Agents write to `agents/<agent-id>/` inside the current session directory and return ≤5 lines; the main thread opens their reports only if needed.

### 2.9 Gating & checkpoints
- For T3 work, write a ≤10-line plan (tasks, classes, roles) to the session context file; proceed without approval unless a step is irreversible or ambiguous.
- Executors start only once their spec is complete with acceptance tests.
- Validate cheaply before expensive steps (dry-run, lint, small sample).
- Fail fast: on a blocking error, stop and report.

### 2.10 Context handoff
- Maintain one session context file in the current session directory (named per `CLAUDE.md`, else `CONTEXT.md`): goal, constraints, decisions, file map, reference index, task table, plan. Update once per milestone.
- Sub-agent briefs contain: task brief + path to the session context file + relevant spec paths + section references to these instructions (by number, not pasted) + any section 8 block marked "verbatim".
- Sub-agents never receive raw thread history.

### 2.11 Batching
- Run independent tool calls in parallel in one turn.
- Commit per milestone, not per file.

## 3. Documentation for Agent Ingestion
All specs and documentation are written primarily to be consumed and updated by future agents at minimum token cost.

### 3.1 Principles
- **Single source of truth:** each fact lives in exactly one document; all others link to it.
- **Current truth only:** history goes in a `## Changelog` section at the end of each document.
- **Self-contained sections:** every section is actionable without reading the rest of the document.
- **Structure over prose:** tables, schemas, and code blocks before paragraphs; stable heading anchors; one topic per section; explicit paths and identifiers.
- **Defined vocabulary:** every name used is defined in a data dictionary; no "e.g." or "etc." in normative text.
- **Docs move with code:** any agent that changes a component updates its spec/docs in the same task; a task is incomplete until docs match code.

### 3.2 Header block (every document)
Purpose · owning component · last updated (session reference ID) · status · links to related specs.

### 3.3 Implementation specs (planner output)
One spec per component, stored where `CLAUDE.md` places specs (else in the current session directory), with this fixed structure:
1. **Purpose** — what the component does and does not do.
2. **Dependencies** — components, libraries (pinned versions), external services.
3. **Data dictionary** — every entity and field: name, type, constraints, nullability, default, example, description.
4. **Data structures** — schemas as code blocks (JSON Schema / TypeScript / SQL DDL / Lua tables as appropriate).
5. **Storage design** — key formats (e.g. `user:{id}:sessions`), value shapes, TTLs, indexes (fields, type, uniqueness, purpose), partitioning.
6. **API contract** — per function/endpoint: signature, typed inputs (validation, required/optional), typed outputs with examples, errors and conditions, idempotency, auth.
7. **Behaviour** — numbered, unambiguous steps per operation, including edge cases.
8. **File map** — exact files to create/modify and their contents.
9. **Acceptance tests** — concrete input → expected output.
10. **Task breakdown** — ordered executor tasks (ID, class, files, depends-on), ready for the task table.

Specs are exhaustive over concise: precision is paid for once by the planner so executors never pay for reasoning.

### 3.4 Generated content
- Extract mechanically derivable content (signatures, parameters, file maps, call sites, indexes) by script from code or structured data; the model writes only descriptions, edge cases, and diagrams.
- Generate summaries, indexes, and reports from structured data (YAML/JSON) in the session directory.

## 4. Session Records & Layout
- The scratch repo structure is defined by `CLAUDE.md`; follow it. This section adds session-level requirements only.
- All paths are **relative to the current session directory** (the session temp root), not the repo root.
- `prompts/` — inside the current session directory:
  - `prompts/NN.md` — each prompt (user and agent-issued), written by script as a verbatim copy plus a one-line summary. Repeated blocks are stored once and referenced by ID.
  - `prompts/README.md` — index: ID, timestamp, author (user/agent), summary, link.
- `README.md` — the session entry point: an **index with summary visuals only**, linking `prompts/README.md`, every report, the reference index, agent outputs, and any test zip. Detail lives in the linked documents, not here.
- Reports, reference index, and test zips go where `CLAUDE.md` places them within the session directory.

## 5. Agent Deliverables
Every agent:
1. Writes all outputs to scratch within its assigned directory.
2. Returns a ≤5-line summary to the orchestrator.
3. Produces a standalone report that:
   - Is understandable without the thread.
   - Uses a session-specific reference ID aligned with the project reference index (e.g. `<INDEX-PREFIX>-<SESSION-ID>-<AGENT-ID>-<NNN>`).
   - Lists inputs, method, findings, artefacts (repo paths), open issues, next steps.
   - Follows section 3.

## 6. Report Content
- Use a visual wherever it replaces prose; at most one per finding: Mermaid (`flowchart`, `sequenceDiagram`, `xychart-beta`, `pie`, `gantt`, `quadrantChart`), emoji heat-map tables (🟥🟧🟨🟩), or ASCII graphs where Mermaid is unsuitable.
- Where testing is relevant, package test material as a zip and link it from the report and the session `README.md`.

## 7. Peer-Review Documentation Standard
Applies whenever a task requests implementation documentation for peer review. Mark it **DRAFT — for peer review**. Build the skeleton by script (3.4); the model fills judgement content.

### 7.1 Per API (every API built or changed: public/internal functions, event handlers, callbacks, exposed interfaces)
1. **Name & signature** — identifier, parameters, return values.
2. **Inputs** — name, type, required/optional, valid range/format, default, example.
3. **Outputs** — return values and side effects (state, saved variables, events, UI), with examples.
4. **Errors & edge cases** — conditions and handling.
5. **Traffic flow** — callers, callees, triggering events, data movement; Mermaid sequence/flow diagram per significant flow.
6. **Architectural position** — module/layer, dependencies, dependents.

### 7.2 Document level
- Architecture overview (Mermaid module/layer diagram).
- End-to-end flow diagrams for each main user-facing or event-driven path.
- Data structures: every table/object/saved variable with fields, types, defaults, examples.
- File map.
- Open questions / known limitations.

### 7.3 Format
Follows section 3. Exhaustive: never omit an API for brevity.

## Interface: the PSS window (PourSocialScore_GUI)
The one place for the window's rules. Details (decisions, code map, lessons): `docs/pss/09_PSS_UI_PROJECT.md`; look numbers: scratch `docs/latest/ui uplift/04_LOOK_SPEC.md`.

### Every element works in all three looks (the first rule)
Three looks (option `uiSkin`), listed in this order everywhere (Options, docs):
1. **Modern** (value 2, **the default**): Blizzard's 12.x Social window art.
2. **Classic** (value 0): Blizzard's classic templates; internal name "blizzard".
3. **Dark** (value 1): the EllesmereUI port's flat style.

The saved values never change (old saves keep their look). Nothing ships that works or looks right in only one or two looks.
1. **One element, three paints.** Every control, row, pane, popup, menu and tooltip is built once, with the parts each look needs, and painted by the look shown (`ns.OnPaint`; Dark parts in `widget.pssParts`). Switching the look or the font (`uiFont`) repaints in place, with no reload.
2. **Only the paint differs.** Layout, sizes, places, text, behaviour, keys (Escape, Back, Enter) and numbers are identical in all three. A look never adds, hides or moves a feature.
3. **Modern falls back to Classic** where the client has no Modern art (Camelot, or a missing atlas): check the art, never assume it. Dark falls back to its own parts when a Blizzard template is missing.
4. **Use the kit, not raw frames:** `ns.NewButton`, `ns.NewCheck`, `ns.NewEditBox` / `NewNumberBox` / `NewSearchBox`, `ns.NewPanel`, `ns.NewRows`, `ns.NewTab`, `ns.NewDropdown` / `ns.ContextMenu` (Blizzard's Menu API in Modern and Classic, our list in Dark or without the Menu API), `ns.Tip` (GameTooltip in Modern and Classic, ours in Dark), `ns.Confirm` / `ns.CopyText` / `ns.ImportText` (the window's frame art, `ns.NewFrameArt`, in Modern and Classic; the flat panel in Dark). A new kind of control is added to the kit in all three looks first, and to the kit preview (`tools/harness/kit_page.lua`).
5. **Per element, check:** its Modern art, its Classic template, its Dark parts; text faded with `SetAlpha`, never colour alpha; lines and edges one physical pixel (`ns.OnePixel`, `ns.NoSnap`); the accent is the class colour (`ns.Accent()`) in every look, with no option; fonts through `ns.Font` so `uiFont` applies (LibSharedMedia only read, only when another addon loaded it); anything that must show over Blizzard frame art sits on a frame raised above its NineSlice (level about 500).
6. **Prove it in all three looks:** `sh tools/harness/tui_compare.sh` (the window step by step in Modern, Classic and Dark; "identical" for a change that should not show, only the intended lines otherwise), `check_tui.lua` (the kit in every look), and in-game checks that name each look, on Retail and Camelot.
