# PourSocialScore: rules and context for Claude

**Highest priority, above every rule below (full text: `docs/pss/11_PREFERENCES.md`):** spend tokens strictly and sparsely; recycle tokens, threads and tools; write as few messages as possible. A required message goes in scratch `temp/YYYY-MM-DD-<workspace>/<output>/` (never the session), with a summary and references in that output's `README.md`, ending with a table of the recent prompts, answers and outputs (all links reference-style at the bottom); every prompt is also logged in the workspace's `prompts/` (`DEC-00036`, `DEC-00038`); tell the author in one line to review it there. Memory holds only the folder's link.

## Reference framework: mandatory for every document (issue #184, `ISS-00001`)
No exceptions without the author's OK. Read before writing any document: scratch `documents/reference-framework/` (`REGISTRY.md` the next integer per type, every key and every retirement; `refkey.py` alloc, retire and check; `00_APPENDIX.md`; `01_ARCHITECTURE.md`; `02_HIGH_LEVEL_DESIGN.md` key shape, types, document set, decisions; `03_DETAILED_DESIGN.md` registry format, allocation, how to write a key, headings, `SAV` rows; `04_IMPLEMENTATION_PLAN.md`).
- **Keys are `<TYPE>-<NNNNN>`**: a 3-letter type, 5 digits from `00001`, one counter per type, project wide; never reused, renumbered, guessed or typed by hand. Types: `CMP` component, `ARC` architecture, `HLD` high level design, `DDS` detailed design, `IMP` implementation plan, `STP` implementation step, `ISS` issue, `APX` appendix, `SAV` SavedVariables decision, `DEC` decision, `TST` test, `CHK` in-game check, `BLD` build record, `RET` retirement. A new type needs the author's OK.
- **The registry is the only source of the next integer:** allocate with `python3 documents/reference-framework/08_Operations/registry-tool/refkey.py alloc <TYPE> <CMP-key> <file> "<title>"` on a freshly pulled scratch `main`, and push the registry before the key is used anywhere. `refkey.py check` before every scratch docs commit must report 0 problems. Run it also after every pull of scratch: a problem anyone left is fixed in the next commit with a changelog row and named in the temp output (`DEC-00042` option C, `STP-00043`; commits are never blocked, nothing runs on GitHub).
- **Every component** lives in scratch `docs/components/<slug>/` with `README.md`, `00_APPENDIX.md` (`APX`), `01_ARCHITECTURE.md` (`ARC`), `02_HIGH_LEVEL_DESIGN.md` (`HLD`), `03_DETAILED_DESIGN.md` (`DDS`), `04_IMPLEMENTATION_PLAN.md` (`IMP`, steps `STP`, tests `TST`, checks `CHK`) and `issues/ISS-<NNNNN>.md`; decisions are `DEC`; every saved key, layout, migration, cap or retirement is a `SAV`. The appendix lists every key of the component, from the registry.
- **Every documentation folder carries `00_APPENDIX.md` (its keys) and `00_References.md` (its retirements and mappings; an empty table until the first)**, created with the folder's first document.
- **Retire, never delete (`RET`, scratch `DDS-00001:7`):** when an item is replaced, merged, split or dropped, allocate the replacement first, then `python3 documents/reference-framework/08_Operations/registry-tool/refkey.py retire <OLD> <NEW|-> <CMP-key> <folder>/00_References.md "<reason>"` (next `RET`, old ledger row marked "(retired, RET-n)", mapping row in the registry); push the registry, copy the row into that folder's `00_References.md`, mark the old definition "(retired, RET-n)" (keep its text), add both keys to `00_APPENDIX.md` and point live documents at the new key. Legacy keys are retired the same way when their component is backfilled. Out-of-date context then still says what replaced it and why.
- **A key is defined once** (its row or heading starts with it) and quoted everywhere else; a place in a document is `KEY:section`. PRs, commits, issues, history and code comments quote keys, never allocate them; the addon repo never holds a registry.
- Legacy series (`ADM-*`, `APR-*`, `ACPI-*`, `EC-*`, `IRE-*`, `ISS-<n>`) are frozen aliases in the registry: read them, never extend them.
- Put this block in every subagent's brief that writes a document.

Every TOC, the history section and the zip name carry it. **`versions.json`** (repo root; `tools/versions.py`) records the latest release, every pre-release since it in order with its PR, and each past release with its pre-releases: references only, never shipped (not in a release zip, test zip or the mirror). The pipeline publishes a full release only for the version `versions.json` names the latest release, and refuses an unrecorded one. Bump with `sh tools/bump_version.sh build "Title"` (`release "Title"`, `line X.Y.Z "Title"`), then `sh tools/bump_version.sh pr <number>` once the PR is open; the rules check fails a missing or wrong PR in CI, a placeholder history bullet, and a history.txt whose top section is not the TOC version. Older names (`-devNNN`, `_N`, plain `3.3.1`) stay as they were.
- **Full releases** (checklist `docs/pss/05_RELEASE.md`, Full releases): list the PRs since the previous release (`python3 tools/versions.py prs <version>`, after `bump_version.sh release`), read each through the GitHub tools, and write **one player-facing summary of all the changes** as the release's history section (no per-build lists, no PR text). The same delivery writes on scratch `docs/latest/release-notes/<version>.md` (the summary, every change in order with build and PR, links to the technical notes; index in its `README.md`) and the release's rows in `docs/latest/summary-of-changes/SUMMARY_OF_CHANGES.md`; refreshes the code map in full (its `README.md` naming the build); re-summarizes `01_HANDOVER.md`; refreshes 13; copies the PSS docs to scratch `docs/latest/pss-docs/`. Full releases are mirrored to `racetracks/Pour-Social-Score` (job `mirror`, secret `MIRROR_TOKEN`): the zip's contents committed as that repo's files and the release on that commit. Pre-releases keep their history section as notes and are not mirrored. No Claude API summary in the pipeline.
- Everything on `M` via `PourSocialScore_NS`; core fires `M.Events`; UIs write only through core setters. Tabs everywhere.
- Core holds only the chat filtering engine and the launchpad; anything not regularly active, or shared by both UIs, goes in `PourSocialScore_Libraries`, with a measured resident cost.
- No application or service logic in `PourSocialScore_GUI`. The old EllesmereUI window is in git history (tag `v3.4.0.24`).
- Every number the window shows comes from the core's counters, the same definitions as before (`check_viewquery.lua`). Logging loads only when logs are called.
- Taint and secrets (baseline 02 J, PSS 02 section 10): never write or replace Blizzard state; post-hooks and `Menu.ModifyMenu` only; every chat, unit and hook value goes through `M.PSS_IsSecret` before any compare or index; a secret line is neither filtered nor counted.
- Never change TOC Title or Notes. SavedVariables layout changes need the author's OK and a migration validated on every real save.
- **Every saved field is in the schema map** (`PourSocialScore/PSS_Schema.lua`; `check_schema.lua` in the rules check and the harness). A newer version's data is never deleted: only `RETIRED` keys go, unknown fields and layouts (`v` above what this version writes) are kept, and a rule this version cannot use is kept, not applied and reported (PSS 02 section 3).
- Never write to `racetracks/PourSocialScore-EllesmereUI` (retired). Read only: `EllesmereGaming/EllesmereUI` (all rights reserved; the UI element reference, 03 section 0), `Gethe/wow-ui-source`.
- **Simulate the WoW client while you code (required; full text in 11):** drive every changed path in the harness's simulated client (`wow_stub.lua` via `run.lua`: load a save, fire the events, commands and clicks, read the real output); give changed behaviour a check that fails on `origin/main`; say in the PR what the simulation cannot show (wrapped text, combat and chat lockdown timing, taint, client art) and put that in the in-game checks; put this in every subagent's brief. Run every test yourself before handover and report what ran and what skipped (CI is only the backstop).
- **Every feature's design and plan name its tests** (PSS 02 section 1.7): per stage, the rules check, the harness checks, the upgrade and data checks, the window compare (`tui_compare.sh`, all three looks) and the real-save run; the release stage also names every release workflow job it needs (`release.yml`, the mirror, the scratch record) and checks it at release.
- Before pushing: `sh tools/check_rules.sh` (it also runs `check_toc.sh` on every folder and the PSS-names check), `PSS_REAL_SAVES=<out dir> sh tools/harness/validate_all.sh` on the saves built from scratch (below; includes `check_tui.lua` and every tab's check; add `PSS_SAME_AS=origin/main` for a stage that must not change the saved data, `same_saves.sh`), and `tui_compare.sh` (all three looks) for any change that should not show.

## Interface: the PSS window (PourSocialScore_GUI)
The one place for the window's rules. Details (decisions, code map, lessons): `docs/pss/09_PSS_UI_PROJECT.md`; look numbers: scratch `docs/latest/ui uplift/04_LOOK_SPEC.md`.

### Every element works in all three looks (the first rule)
Three looks (option `uiSkin`), listed in this order everywhere (Options, docs):
1. **Modern** (value 2, **the default**): Blizzard's 12.x Social window art.
2. **Classic** (value 0): Blizzard's classic templates; internal name "blizzard".
3. **Dark** (value 1): the EllesmereUI port's flat style.

The saved values never change (old saves keep their look). Nothing ships that works or looks right in only one or two looks.
1. **One element, three paints.** Every control, row, pane, popup, menu and tooltip is built once, with the parts each look needs, and painted by the look shown (`ns.OnPaint`; Dark parts in `widget.pssParts`). Switching the look or the font (`uiFont`) repaints in place, with no reload.
2. **Only the paint differs.** Layout, sizes, places, text, behaviour, keys (Escape, Back, Enter) and numbers are identical in all three. A look never adds, hides or moves a feature.
3. **Modern falls back to Classic** where the client has no Modern art (Camelot, or a missing atlas): check the art, never assume it. Dark falls back to its own parts when a Blizzard template is missing.
4. **Use the kit, not raw frames:** `ns.NewButton`, `ns.NewCheck`, `ns.NewEditBox` / `NewNumberBox` / `NewSearchBox`, `ns.NewPanel`, `ns.NewRows`, `ns.NewTab`, `ns.NewDropdown` / `ns.ContextMenu` (Blizzard's Menu API in Modern and Classic, our list in Dark or without the Menu API), `ns.Tip` (GameTooltip in Modern and Classic, ours in Dark), `ns.Confirm` / `ns.CopyText` / `ns.ImportText` (the window's frame art, `ns.NewFrameArt`, in Modern and Classic; the flat panel in Dark). A new kind of control is added to the kit in all three looks first, and to the kit preview (`tools/harness/kit_page.lua`).
5. **Per element, check:** its Modern art, its Classic template, its Dark parts; text faded with `SetAlpha`, never colour alpha; lines and edges one physical pixel (`ns.OnePixel`, `ns.NoSnap`); the accent is the class colour (`ns.Accent()`) in every look, with no option; fonts through `ns.Font` so `uiFont` applies (LibSharedMedia only read, only when another addon loaded it); anything that must show over Blizzard frame art sits on a frame raised above its NineSlice (level about 500).
6. **Prove it in all three looks:** `sh tools/harness/tui_compare.sh` (the window step by step in Modern, Classic and Dark; "identical" for a change that should not show, only the intended lines otherwise), `check_tui.lua` (the kit in every look), and in-game checks that name each look, on Retail and Camelot.

### Titles and popups
- **Only the main window's title carries the addon's name** ("Pour Social Score"). Popup and dialog titles say what they ask ("Remove Player?", "Remove Guild?", "Remove Rule?", "Prune Players?"), never the addon name, and sit in the title bar in Modern and Classic.
- The window's popups are our own frames (no `StaticPopupDialogs` entries from the window); each registers for Escape through `ns.EscapeCloses` after its own scripts are set. One Escape closes the top popup or menu, then steps the window up one level, then closes it.
- **Core's note and party warning popups stay Blizzard StaticPopups in every look**: core never loads the GUI folder for a popup.

### The other interface rules
- **The EllesmereUI port is the reference** for layout, features and feel (tag `v3.4.0.24`); the old GUI is not authoritative. Blizzard's Social window is the reference for Modern. Copy behaviour and numbers, never EllesmereUI's code or media.
- **EllesmereUI is the reference framework for UI elements:** when building an element needs more information, add `EllesmereGaming/EllesmereUI` to the session (`add_repo`, read only) and reference it wherever possible. Rewrite to our rules (the kit, all three looks, Libraries for logic, PSS names, zero cost, J rules); never copy it verbatim, never its media. How: `docs/pss/03_ELLESMEREUI.md` section 0.
- **Logic in `PourSocialScore_Libraries`, drawing only in `PourSocialScore_GUI`.** No state, query, validation or flow in a drawing file; UIs write through core setters (`check_layers.lua`). No `EUI` or `Ellesmere` names in new code (`check_rules.sh`).
- **Zero cost until opened:** `/pss gui` loads Libraries and the GUI folder; each tab is built on first open; core events are heard only while the window shows (`ns.Listen`); the window drops what it read and requests a GC on close.
- **Taint and secrets:** baseline 02 J and PSS 02 section 10 apply to every UI hook and every unit or chat value the window shows or acts on.
- **Saved state:** window place, last tab and new settings live in `PSS_OptionsDB` (routed `PourSocialScoreDB` UI keys); no new SavedVariables for the window. The one exception: the addon manager's per-character profiles and protected addons live in `PSS_CharDB` (`SavedVariablesPerCharacter` in `PourSocialScore_Options`, nil until used).

## Working in a Claude Code session
Style, file hosting and messages: `11_PREFERENCES.md` (call the user "the author"; files go on scratch, never in the session, replies give links).
- **Fetch fresh repos first, in every session** (`DEC-00053`): before reading anything, `git fetch origin main` (and the session branch) in the addon repo and `git pull origin main` in scratch, then `refkey.py check`; never work from a stale checkout.
- **Install `lua5.1` first, in every session:** `apt-get install -y lua5.1` (`apt-get update` first if not found). The rules check, every harness check and the real-save run need it; never skip a check because it is missing.
- Develop on the session's `claude/...` branch from the latest `origin/main`; one step per PR, based on main; never stack. **One step per session** (baseline 02 E9 to E11): build only the stage named (the next in the current plan's table unless the author names another; several stages in one build need an Overrides row), then stop.
- If `gh` is not available, use the session's GitHub tools instead of the `gh` commands in the packs.
- **Scratch is `racetracks/Pour-Social-Score_Scratch`** (branch `main`; rules in `docs/scratch/05_RULES.md`); the old `racetracks/scratch` is no longer used. Add it to the session (`add_repo`); if it cannot be added, say so and ask. **Never a PR or branch on scratch:** check out `main` and push straight to it, even when the session names a `claude/...` branch (that is for the addon repo). Pull before every change, one commit per delivery, update its `readme.md` index when a folder's newest file changes, and reply with links (`/raw/main/<path>` for downloads, `/blob/` to read, `/tree/` for a folder).
- **Scratch is the project files:** wherever the packs say "project files" or `/mnt/project-files/...`, read scratch: `SavedVariables/<version>/` (saves), `docs/latest/` (plans and docs; read it first: `docs/README.md` is the docs index, `readme.md` the repo index), `releases/` and `latest/` (zips). Each docs release is also zipped in `docs/` (`<name>-<date>-vN.zip`) and a project or feature release keeps a history folder `docs/<project>/`. When a plan or these docs change, refresh `docs/latest/` in the same scratch commit. Status summaries go in `summary/<project>-<YYYY-MM-DD-hh-mm>.md`.
- **Real saves are never committed here** (baseline 02 D10); they live on scratch `SavedVariables/<version>/` (2.0.44, 3.0.0, 3.2.0-dev011, 3.4.0.28, 3.4.1.50). Real-save run: `sh tools/harness/build_saves.sh <scratch checkout> <out dir>` (out dir in the session scratchpad; default `/tmp/pss-baselines`), then `PSS_REAL_SAVES=<out dir> sh tools/harness/validate_all.sh`. If scratch cannot be read, say the real-save run did not happen; never claim it did.
- The clone is shallow: before `validate_all.sh`, run `git fetch --depth=2000 origin main` (its upgrade checks rebuild old versions from history; without it the "split" checks fail on 2.0.1 and 2.0.40).
- Test zips go to scratch `releases/PourSocialScore-<version>-<YYYY-MM-DD-hh-mm>.zip`, and the same commit replaces the zip in `latest/` (scratch rule 9); `sh tools/host_build.sh <scratch checkout>` does it from HEAD (`--no-commit` to add docs to the same commit); link it as `/raw/main/<path>`.
- **Update the context in every PR:** the current project's stage table (state, PR, next build), `06_STATUS_AND_NEXT.md`, `02_RULES.md` for a new rule, `11_PREFERENCES.md` for a new preference, and the scratch copies (`docs/latest/pss-docs/`, the project's folder) in the same delivery, so a fresh session starts from this file alone.
- **At each full release** re-summarize the done stages into `01_HANDOVER.md` and take them out of the plan; this file only points to plans and designs, never copies them. The author's preferences live only in `11_PREFERENCES.md`.
- Blizzard's UI source for a template or atlas question: a sparse clone of `Gethe/wow-ui-source` (for example `Interface/AddOns/Blizzard_SharedXML`, `Blizzard_SocialUI`); read only.
